# 测试与贡献

Syl 编译器通过单元测试、架构合约测试、黄金测试、一致性测试以及 Verilator + Yosys 仿真综合门禁保障质量。以下说明测试运行方式、质量检查项与贡献流程。

---

## 运行测试

Syl 编译器使用 Cargo 管理测试。在仓库根目录运行：

```bash
cargo test
```

这会运行所有 crate 的单元测试和集成测试。

如果你想只运行某个 crate 的测试：

```bash
cargo test -p syl_syntax
cargo test -p syl_sema
cargo test -p syl_elab
```

架构合约测试在 `sylc` crate 中：

```bash
cargo test -p sylc --test architecture_*
```

一致性测试也是独立的：

```bash
cargo test -p sylc --test conformance
```

### 一键质量门禁（`scripts/quality_gate.sh`）

在提交 PR 前，建议运行仓库提供的一键质量门禁脚本：

```bash
./scripts/quality_gate.sh
```

`quality_gate.sh` 按顺序执行以下检查：
1. `cargo fmt --all --check`
2. `cargo clippy --workspace --all-targets -- -D warnings`
3. `cargo test --workspace --all-targets --no-fail-fast`
4. `scripts/parser_fuzz_smoke.sh`（运行 `syl_fuzz` 语料冒烟测试）
5. `scripts/check_examples.sh`（编译示例并运行 Verilator lint 与 `scripts/check_std_sim.sh`）
6. `scripts/check_docs_syl.py`（提取所有 Markdown 中的 ```` ```syl ```` 代码块并验证语法）
7. `scripts/check_public_api.py --check`（公共 API 快照与消费者校验）
8. `cargo doc --workspace --no-deps`
9. `git diff --check`、技术债标记扫描（`MUST_FIX|SHOULD_FIX|FIXME|TODO|HACK|XXX`）与临时文件检查

## 测试体系

Syl 的测试分为五个层次。

### 单元测试（无 inline tests 规范）

每个 crate 内部有针对具体函数的单元测试。它们测试小粒度的行为，比如解析器的某个语法规则、类型检查器的某个检查逻辑。

**无 inline tests 规范**：在 `crates/*/src/` 的所有非测试生产源码文件中，**严禁内联 `#[test]` 块**。单元测试统一放置在独立的 `*tests.rs` / `tests.rs` 子模块或 `crates/*/tests/` 集成测试文件中，保持生产代码与测试代码物理分离。

此外，`crates/sylc/tests/architecture_markers_test.rs` 通过 `architecture_rust_files_stay_under_700_lines` 强制约束每个 `.rs` 文件代码行数小于 700 行。

### 架构合约测试

架构合约测试是一组特殊的集成测试，位于 `sylc/tests/` 目录下。它们的文件名以 `architecture_` 开头：

- `architecture_phase1_ir.rs`：验证每个 IR 单拥有者，端到端编译流
- `architecture_phase2_frontend.rs`：验证前端的解析和恢复行为
- `architecture_phase3_sema.rs`：验证语义分析的公开事实接口
- `architecture_phase4_elab.rs`：验证展开流水线的每个阶段都暴露了输出
- `architecture_phase5_opaque.rs`：验证不透明摘要的注册和查询
- `architecture_phase6_backend.rs`：验证后端输出稳定的 SV 代码
- `architecture_phase7_query_lsp.rs`：验证查询引擎不触发展开
- `architecture_phase8_std.rs`：验证标准库和其他代码走相同流水线

这些合约测试有两个作用：

**第一，维护架构边界。** 每个合约测试都检查 crate 之间的依赖关系是否合规。例如，`syl_sema` 的生产代码不能依赖 `syl_elab`。如果有人在 `syl_sema` 中添加了 `use syl_elab`，合约测试会失败。

**第二，验证阶段输出。** 每个合约测试都检查该阶段的输出是否结构完整。例如，展开阶段的合约测试验证：从 TIR 开始，经过展开流水线，最终输出的 HW IR 可以正确转换为 SystemVerilog。

### 黄金测试

黄金测试（Golden Test）比较编译器输出和预先存储的期望输出。黄金文件位于 `sylc/tests/golden/` 目录下。

例如，`architecture_phase6_backend.rs` 中的一个测试会编译一段 Syl 代码，将输出的 SystemVerilog 和 `golden/phase6_child_top.sv` 文件的内容进行逐字节比较。如果两者不一致，测试失败。

黄金测试的变化需要审慎处理：如果故意修改了输出格式，需要同时更新黄金文件。如果无意中修改了输出格式，黄金测试会发现回归。

### 一致性测试

一致性测试（Conformance Test）检查编译器对特定语言特性的支持和错误检测。测试用例位于 `conformance/` 目录下：

```
conformance/
├── parse/       # 语法解析测试
│   ├── positive/  # 应该通过解析的代码
│   └── negative/  # 应该触发语法错误的代码
├── sema/        # 语义分析测试
│   ├── positive/
│   └── negative/
└── elab/        # 展开测试
    ├── positive/
    └── negative/
```

每个测试用例是一个 `.syl` 文件，配套一个 `.codes` 文件描述期望的诊断信息。

### Verilator 仿真与 Yosys 综合门禁（`scripts/check_std_sim.sh`）

`scripts/check_std_sim.sh` 对 `examples/std/` 下的 6 个核心包（`pulse`、`skid`、`arbiter`、`cdc`、`mem`、`fifo`）执行真实硬件验证：
- **Verilator lint 与 C++ 联合仿真**：使用 `verilator --cc --exe --build` 配合 `tests/sim/<package>_test.cpp` 编译并运行仿真，覆盖 `EdgeDetector`、`PulseStretcher`、`WordSkidBuffer`、`FixedPriorityArbiter4`、`RoundRobinArbiter4`、`Sync2FF`、`Sync2FFAsyncLow`、`PulseSynchronizer`、`SinglePortRam`、`SimpleDualPortRam`、`DistributedRam`、`SyncFifo` 与 `StreamSyncFifo`。
- **Yosys 综合门禁**：当环境中存在 `yosys` 时，对 `mem.sv`（三种 RAM）与 `cdc.sv`（`Sync2FFAsyncLow`）运行 `hierarchy -check; proc; memory; check -assert; stat`，确保生成代码可综合。

## 代码质量检查

Syl 使用以下工具保证代码质量：

**Cargo clippy。** 运行 Rust 的 lint 工具：

```bash
cargo clippy --workspace --all-targets -- -D warnings
```

**公共 API 快照校验。** 通过 `scripts/check_public_api.py --check` 提取所有工作区库 crate 的 rustdoc JSON，禁止公共 glob 重导出，并与 `api/public-surface.txt` 逐项比对，同时校验 `api/public-api-consumers.md` 中的消费者登记。

**Mermaid 检查。** 文档中的 mermaid 图需要经过语法校验：

```bash
pnpm check:mermaid <mdx-file>
```

**阅读时间检查。** 每篇文档的阅读时间需要落在 6 到 20 分钟之间：

```bash
pnpm check:readtime <mdx-file>
```

## 贡献流程

### 报告问题

在 GitHub Issues 中报告 bug 或提出功能请求。报告 bug 时请包含：

- 观察到的问题描述
- 期望的行为
- 最小可复现示例
- 环境信息和诊断输出

### 提交 PR

提交 Pull Request 时请遵循以下原则：

**聚焦。** 一个 PR 只解决一个问题。无关的修改请放在另一个 PR 中。

**说明改动原因。** 在 PR 描述中解释改了什么、为什么改、如何验证。

**标注用户可见影响。** 如果改动改变了命令行接口的输出、新增或修改了诊断信息、影响了公共 API，请在 PR 描述中明确说明并同步更新 `api/public-surface.txt`。

**更新测试。** 新增功能需要配套测试，修复 bug 需要添加回归测试。

**通过 CI。** 提交前在本地运行 `./scripts/quality_gate.sh`，确保不会引入回归。
