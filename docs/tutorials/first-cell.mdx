# Lesson 1: Your First Cell

In this lesson, you will write your first hardware module—called a **`cell`** in Syl—verify it with `sylc check`, intentionally trigger compile-time hardware errors to see how the compiler protects you, and inspect the SystemVerilog generated by `sylc emit`.

## Learning Objectives

By the end of this lesson, you will be able to:

- Verify your `sylc` installation and run `sylc check` and `sylc emit`.
- Declare a combinational `cell` with typed input ports (`in`) and a named output (`->`).
- Group related output signals using a `bundle`.
- Explain why Syl separates continuous hardware driving (`:=`) from software assignment, and how static single-driver checking prevents multi-driver bugs.
- Read the MVP SystemVerilog emitted by `sylc`.

## Prerequisites

- `sylc` installed and available in your shell (`sylc --version` outputs `sylc 0.1.0`).
- A working directory for your scratch files (for example, `mkdir -p ~/syl-tut1 && cd ~/syl-tut1`).

## Step 2: A Minimal Combinational Cell

Create a file named `alu_add.syl` with a single combinational `cell` that adds two 8-bit unsigned integers:

```syl
cell Add8(
    a: in UInt<8>,
    b: in UInt<8>,
) -> sum: UInt<8> {
    sum := a + b
}
```

Let's break down every token:

- **`cell Add8(...)`**: Declares a hardware module named `Add8`. Unlike a software function that executes sequentially and returns once, a `cell` describes a physical circuit block that exists continuously in hardware.
- **`a: in UInt<8>`**: Declares an 8-bit unsigned input port `a`. Notice that the port name comes before the colon, followed by the direction (`in`) and the bit-accurate type (`UInt<8>`).
- **`-> sum: UInt<8>`**: Declares the cell's output port `sum` of type `UInt<8>`.
- **`sum := a + b`**: Drives the output wire `sum` continuously with the 8-bit sum of `a` and `b`. Syl uses `:=` (rather than `=`) to emphasize **hardware signal driving**: it is a permanent physical connection, not a sequential variable mutation.

Run the compiler's static checker:

```bash
sylc check alu_add.syl
```

If everything is valid, `sylc check` exits with status `0` and produces no output.

## Step 3: Evolving the Design with `bundle` and `select priority`

Real hardware blocks rarely have a single raw output. Suppose we want our adder to also support bitwise XOR (controlled by `use_xor: in Bit`) and report whether the result is zero (`is_zero: Bit`).

Update `alu_add.syl` as follows:

```syl
bundle AddResult {
    sum: UInt<8>,
    is_zero: Bit,
}

cell AluAdd8(
    a: in UInt<8>,
    b: in UInt<8>,
    use_xor: in Bit,
) -> rsp: AddResult {
    signal val: UInt<8> :=
        select priority {
            use_xor => a xor b,
            default => a + b,
        }

    rsp := AddResult {
        sum: val,
        is_zero: val eq 0,
    }
}
```

### Why This Works (Hardware Semantics)

1. **`bundle AddResult`**: Packs `sum` (8 bits) and `is_zero` (1 bit) into a single composite wire type. In SystemVerilog, this lowers to a packed 9-bit vector `[(8 + 1)-1:0]`.
2. **`signal val: UInt<8>`**: Declares an internal combinational wire. Because `val` is a `signal` (not a `reg`), it has no clock and no memory—it is purely combinational logic.
3. **`select priority { ... }`**: Describes a priority multiplexer. When `use_xor` is `1`, `val` is driven by `a xor b`; otherwise, `default` selects `a + b`. Requiring a `default` branch guarantees that `val` is never left undriven (preventing accidental latches).
4. **`val eq 0`**: Hardware equality comparison uses `eq` (and produces a `Bit`). Syl reserves `==` and `>` for compile-time constant/proposition expressions.

Run `sylc check` again:

```bash
sylc check alu_add.syl
```

Exit code `0`—the design is statically verified.

## Step 4: Emit and Inspect SystemVerilog

Now let's compile `AluAdd8` into SystemVerilog:

```bash
sylc emit alu_add.syl
```

Output:

```verilog
// Generated by sylc. MVP SystemVerilog subset.

module AluAdd8 (
    input [7:0] a,
    input [7:0] b,
    input use_xor,
    output [(8 + 1)-1:0] rsp
);
  wire [7:0] val;
  assign val = /* priority */ (use_xor ? (a ^ b) : (a + b));
  assign rsp = {val, (val == 0)};
endmodule
```

Notice how directly Syl maps to synthesis-ready SystemVerilog:
- `signal val: UInt<8>` becomes `wire [7:0] val;`.
- `select priority` becomes a ternary `assign` expression.
- `AddResult { sum: val, is_zero: val eq 0 }` becomes a packed concatenation `{val, (val == 0)}`.

## Step 5: What `sylc` Catches at Compile Time

In traditional Verilog, driving the same `wire` from two `assign` statements compiles silently and produces `X` (unknown) contention in simulation. In Syl, every signal must have **at most one driver** (and every output must have **at least one driver**).

Try creating `bad_driver.syl`:

```syl
cell BadDriver(
    a: in UInt<8>,
    b: in UInt<8>,
) -> sum: UInt<8> {
    sum := a
    sum := b
}
```

Run `sylc check bad_driver.syl`:

```text
error[E_MIDDLE_DUPLICATE_HARDWARE_DRIVER]: duplicate hardware driver for sum
  --> bad_driver.syl:6:5
   |
 6 |     sum := b
   |     ^^^^^^^^
   |
note: previous driver claim
  --> bad_driver.syl:5:5
   |
 5 |     sum := a
   |     ~~~~~~~~
   |
note: conflicting driver claim
  --> bad_driver.syl:6:5
   |
 6 |     sum := b
   |     ~~~~~~~~
   |
error: aborting due to 1 previous errors
```

`sylc` immediately rejects the conflicting drivers with `E_MIDDLE_DUPLICATE_HARDWARE_DRIVER` before any simulator is invoked.

## Common Pitfalls

- **Using `in a: UInt<8>` instead of `a: in UInt<8>`**: Syl places the port identifier before the colon (`name: direction Type`).
- **Using reserved keywords as port names**: Words like `out`, `in`, `reg`, and `signal` are reserved. Use `rsp`, `result`, or `dout` for output ports.
- **Using `>` or `==` in hardware expressions**: Syl separates software/const operators from hardware operators, reporting `E_MIDDLE_SOFTWARE_OP_IN_HARDWARE` if you use `>` on a `signal`. Use `eq` for hardware equality.
